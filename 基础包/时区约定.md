# Auth 系统时区规范指南

## 1. 目的与原则

为解决前后端与数据库之间因时区不一致导致的计算偏差、审计异常及展示混乱问题，本规范定义了 Auth 系统关于“时间”数据的统一处理约定。

系统整体遵循以下基本原则：

- **瞬时点（创建/更新、登录、过期、审计等）：** 后端、数据库与接口统一以 **协调世界时（UTC）** 作为存储与交互标准。
- **用户终端（前端界面）：** 统一根据 **浏览器本地时区** 进行转换展示。
- **定时任务（调度服务）：** 采用带有明确时区属性的 **墙钟时间（Wall Clock Time）**，与瞬时点字段分属不同语义，不适用上述 UTC 唯一标准。

相关基础设施搭建请参考 [[3-中间件-Compose]] 与 [[5-Nacos配置导入]]；本机启动见 [[8-本地启动前后端]]。任务调度的墙钟语义以调度模块实现为准。

## 2. 时间类型与转换标准

> [!IMPORTANT] 强制规范
> 严禁在业务代码中硬编码 `Asia/Shanghai` 或其他特定时区来格式化 `createdAt`、`expires` 等瞬时点字段。东八区或特定时区属性仅允许出现在定时任务等需要按照当地墙钟运行的配置中。

业务开发中应严格遵循下表定义的类型、存储方式与时区语义：

| **时间类型**          | **应用场景**                    | **数据库 / 编程语言类型**                                              | **时区语义及规范**                                                                                        |
| ----------------- | --------------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| **瞬时点（Instant）**  | 创建/更新时间、登录时间、令牌过期时间、日志审计等   | MySQL: `datetime(3)`<br><br>Java: `Instant`                   | **标准 UTC**<br><br>库中存无时区偏移的数字，约定语义为 UTC（非 MySQL `TIMESTAMP` 类型，亦非 epoch）；严禁转换为本地时区后存库。             |
| **瞬时点（epoch 毫秒）** | 在线用户最近登录等（Redis ZSet score） | Java: `Long`<br><br>JSON: 数字毫秒（例：`1785409318774`）             | **仍是 UTC 绝对时刻**<br><br>与 `Instant` 同属瞬时点，仅因 Redis 索引形态用毫秒；可多时区展示。勿改成无偏移 `yyyy-MM-dd HH:mm:ss`。     |
| **接口 JSON 传输**    | API 接口入参与出参（主流业务字段）         | ISO-8601 标准字符串<br><br>（例：`2026-07-28T10:06:00Z`）              | **标准 UTC（带 Z 标识）**<br><br>禁用无时区偏移的 `yyyy-MM-dd HH:mm:ss` 格式。在线用户 `lastLoginAt` 等 epoch 毫秒字段除外，见上表。 |
| **前端展示与筛选**       | 列表展示、详情查看、时间范围筛选组件          | 前端 `formatDateTime` / `formatMillisTimestamp`、Instant 选择器     | **浏览器本地时区**<br><br> ISO 串用 `formatDateTime`；毫秒时间戳用 `formatMillisTimestamp`，二者展示语义一致。               |
| **调度墙钟时间**        | Cron 表达式、定时任务起止时间           | Java: `LocalDateTime`<br><br>库列: `time_zone`；接口字段: `timeZone` | **墙钟时间**<br><br> 需显式指定时区属性（未填写时默认 `Asia/Shanghai`）。                                                |

## 3. 运行环境配置要求

系统运行时，必须确保 JVM、JSON 序列化组件及 JDBC 数据库连接三处的时区配置保持高度一致。

### 3.1 JVM 运行时配置

在 Docker 环境或 IDE 本机启动参数中，必须显式指定 JVM 默认时区为 UTC：

```Plaintext
-Duser.timezone=UTC
```

> Docker Compose 部署文件已在 `JAVA_TOOL_OPTIONS` 中包含该配置（详见 `auth-server/docker/compose.yml`）。

### 3.2 Jackson 序列化配置

在各微服务的 `application.yml` 中，须配置 Spring Boot 默认的 Jackson 行为，确保瞬时点统一序列化为包含 `Z` 标识的 ISO-8601 格式：

```YAML
spring:
  jackson:
    time-zone: UTC
    serialization:
      write-dates-as-timestamps: false
```

### 3.3 JDBC 及 Nacos 数据库连接配置

数据库连接 URL 必须显式设置 `serverTimezone=UTC`，建议配合 Hikari 连接池的初始化 SQL 将会话时区固定为 UTC：

```YAML
spring:
  datasource:
    url: jdbc:mysql://<host>:3306/<db>?serverTimezone=UTC&useSSL=false&characterEncoding=utf-8&allowPublicKeyRetrieval=true&rewriteBatchedStatements=true
    hikari:
      connection-init-sql: SET time_zone = '+00:00'
```

## 4. 前端交互与处理规范

为保证多时区兼容性，前端模块在处理时间数据时必须统一调用公共工具（`dateTime.ts` 的 `formatDateTime`，以及会话侧 `sessionTime.ts` 的 `formatMillisTimestamp`）。公共工具内部可使用 `dayjs`；禁止在业务页面中自行按特定时区硬编码格式化瞬时点，或绕过公共方法私自拼接无偏移时间串。

| **交互场景**                   | **调用规范**                                                        | **规范说明**                                                   |
| -------------------------- | --------------------------------------------------------------- | ---------------------------------------------------------- |
| **列表 / 详情显示（ISO Instant）** | `formatDateTime(...)`                                           | 公共审计列已集成该逻辑，系统自动根据浏览器时区渲染展示。                               |
| **列表显示（epoch 毫秒）**         | `formatMillisTimestamp(...)`                                    | 用于在线用户 `lastLoginAt` 等毫秒字段；与 `formatDateTime` 同为浏览器本地时区展示。 |
| **瞬时点条件筛选**                | `INSTANT_PICKER_VALUE_FORMAT`<br><br>（`YYYY-MM-DDTHH:mm:ssZ`）   | 传参时必须包含 ISO 时区偏移标识符 `Z`。                                   |
| **调度任务起止时间选择**             | `WALL_CLOCK_PICKER_VALUE_FORMAT`<br><br>（`YYYY-MM-DDTHH:mm:ss`） | 提交无时区偏移的墙钟时间字符串，配合任务配置的 `timeZone` 字段生效（对应库列 `time_zone`）。 |

## 5. 验收与验证步骤

系统部署或本地启动后，请按以下步骤验证时区配置是否准确：

1. **接口层验证**：打开浏览器开发者工具（Network 标签页），查看业务接口返回的 JSON 报文。例如 `createTime` 应返回 `2026-07-28T10:06:00Z` 格式，而非 `2026-07-28 18:06:00`。在线用户接口的 `lastLoginAt` 可为毫秒数字，属约定形态。
2. **持久层验证**：直接查询数据库，`create_time` 字段值应接近 `UTC_TIMESTAMP(3)`。在东八区环境下，前端界面显示的本地时间应比数据库存储的值快 8 小时。
3. **跨时区表现验证**：手动修改浏览器/操作系统时区后刷新页面，接口返回的字符串（或毫秒数字）不变，前端界面渲染的时间自动按新时区折算，系统鉴权与逻辑判断正常。
4. **任务调度验证**：按任务自身的 `timeZone`（未填则默认 `Asia/Shanghai`）配置墙钟时间为“次日 09:00”的定时任务，系统应在该任务时区下的墙钟 09:00 触发执行，与瞬时点字段及操作系统/浏览器时区无逻辑绑定。

## 6. 注意事项

1. **宿主机时区与应用时区隔离**：宿主机执行 `timedatectl set-timezone Asia/Shanghai` 仅影响操作系统命令行工具显示。Docker 容器与 JVM 依然依赖 `-Duser.timezone=UTC` 配置。
2. **数据库数值理解**：数据库内存储的时间数值较当前北京时间早 8 小时属于正常现象，代表约定语义下的 UTC 刻度，非系统异常或数据缺失。
3. **定时任务为何允许配置上海时区**：Cron 与起止时间为墙钟语义，必须携带 `timeZone`（库列 `time_zone`）；与 `create_time`、`expires` 等瞬时点字段不是同一类数据，允许默认 `Asia/Shanghai` 并不违反瞬时点 UTC 契约。
4. **在线用户 `lastLoginAt`（毫秒）**：与 `createTime`（`Instant` ISO）同属瞬时点，仅因 Redis 在线索引以 epoch 毫秒为 score，接口以 `Long` 返回；多时区展示能力等价，不算偏离 UTC 契约。
5. **导出文件与邮件文本处理**：目前部分后台导出文件或系统邮件通知可能直接输出 UTC 时间，该表现为已知设计边界，请勿为了满足特定文案展示而更改后端的 UTC 时区契约。
