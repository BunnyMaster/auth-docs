## 审查维度（请逐一分析）

### 1. 主键设计合理性

- 是否每张表都有主键？
- 主键是否使用自增整型 / UUID / 雪花 ID？日志表是否适合使用业务字段作为主键？
- 是否存在复合主键导致索引过大或写入性能下降？

### 2. 外键约束设置

- 是否使用了物理外键？在日志表中使用外键是否合理（考虑高并发写入时的锁影响）？
- 外键的级联删除/更新策略是否恰当（如 ON DELETE CASCADE 可能导致意外数据丢失）？
- 外键引用的父表字段是否有索引？是否存在外键引用错误（类型不一致、字段不存在）？

### 3. 字段命名与语义

- 字段命名是否符合项目统一的命名规范（如 snake_case，布尔字段以 `is_` 或 `flag_` 前缀）？
- 是否存在无业务含义的字段名（如 `data`，`info`，`temp`，`value`）？
- 字段名是否与 MySQL 保留字冲突（如 `key`，`order`，`group`）？

### 4. 数据类型与配置

- 时间字段是否统一使用 `datetime` / `timestamp`？有无误用 `varchar` 存储时间的反模式？
- IP 地址字段是否使用 `varchar(45)` 而非 `int unsigned`（权衡可读性与性能）？
- JSON 字段是否滥用？是否应该拆分为子表？
- 字段长度/精度是否合理（如 `varchar(255)` 过大，`decimal` 未指定精度）？
- 默认值（DEFAULT）和空值约束（NOT NULL）是否符合业务语义？日志表的必填字段是否合理设置了 NOT NULL？
- 时间是否 create_time、update_time 是否有默认值？

### 5. 索引配置

- 是否存在重复索引或冗余索引（如单列索引 `(user_id)` 和联合索引 `(user_id, create_time)` 中的前者冗余）？
- 日志表的索引是否过多导致写入变慢？是否存在未使用到的索引？
- 外键列是否缺少索引（导致级联更新/删除时锁表）？
- 常用查询字段（如 `create_time`，`user_id`，`operation_type`）是否有合适的索引？

### 6. 表间关系与一致性

- 日志表与业务主表（如用户表）的外键关系是否合理？是否因为主表数据删除导致日志外键失效或需要补充逻辑？
- 是否存在循环外键或自引用外键设计错误？
- 字符集与排序规则（CHARSET/COLLATE）是否与关联表一致（避免隐式转换）？
