# 更新用户授权边

## 痛点

授权边一变，Redis 里的 `AuthProfile` 必须跟着变。漏刷 = 用户还拿着旧权限/旧数据范围；滥刷 = 无关用户被 `permVersion` 踢来踢去。

所以：**不是全站刷**，而是 `ChangeKind → Impact 反查 → 命中用户` 再整包重建画像。

## 契约 Kind（以代码为准）

`AuthorizationChangeKind` 只有这六个：

| Kind | 典型触发场景 | Payload 业务键 |
|------|-------------|----------------|
| `ROLE` | 角色码/状态/删除、角色赋权、`role_scope` | `roleCodes` |
| `PERMISSION` | 权限码/状态/删除 | `permissionCodes` |
| `GRANT` | 组织主体（DEPT/POST）替换 `grant_table` | `GrantSubjectKey` 列表 |
| `USER_DEPT` | **部门主数据** parent/status/删除（反查成员） | `deptIds` |
| `USER_POST` | **岗位主数据** status/删除（反查成员） | `postIds` |
| `USER` | 已知 `userId`：成员边、`user_scope`、用户直连角色、用户主档相关 | `userIds` |

> [!IMPORTANT]
> 没有 `USER_SCOPE`。用户数据范围走 **`USER`**。
> `USER_DEPT` / `USER_POST` **不是**成员边 Kind，是部门/岗位主数据变更后「找谁该刷」用的反查入口。

## 必须失效的操作（现接线）

| 操作 | Kind | Trigger / 入口 |
|------|------|----------------|
| 组织主体替换角色（DEPT/POST → `grant_table`） | `GRANT` | `GrantAuthorizationInvalidationTrigger` ← `GrantTableServiceImpl.replaceOrgSubjectRoles` |
| 用户直连替换角色 | `USER` | `UserAuthorizationInvalidationTrigger` ← `SysUserRoleServiceImpl`（内部改 `grant_table`，失效不走 GRANT） |
| 角色分配权限 | `ROLE` | `RoleAuthorizationInvalidationTrigger` ← `SysRolePermissionServiceImpl` |
| `role_scope` 变更 | `ROLE` | 同上 Trigger ← `SysRoleScopeServiceImpl` |
| `user_scope` 变更 / 清空 | `USER` | `UserAuthorizationInvalidationTrigger` ← `SysUserScopeServiceImpl` |
| `user_dept` / `user_post` 增删改清 | `USER` | 同上 Trigger ← `SysUserDeptServiceImpl` / `SysUserPostServiceImpl` |
| 部门 parent / status / 删除 / move | `USER_DEPT` | `DeptAuthorizationInvalidationTrigger` ← `SysDeptServiceImpl` |
| 岗位 status / 删除 | `USER_POST` | `PostAuthorizationInvalidationTrigger` ← `SysPostServiceImpl` |
| 角色 roleCode / status / 删除 | `ROLE` | `RoleAuthorizationInvalidationTrigger` ← `SysRoleServiceImpl` |
| 权限 permissionCode / status / 删除 | `PERMISSION`（删除时若仍有绑定角色，再补 `ROLE`） | `PermissionAuthorizationInvalidationTrigger` + 可选 `Role…` ← `SysPermissionServiceImpl` |

## Impact 反查：谁会被刷

由 **ChangeKind → ImpactResolver** 决定用户集合，入口在 `InvalidationImpactResolverConfiguration` / `AuthorizationImpactMapper`。

| Kind | 影响用户范围 |
|------|-------------|
| **ROLE** | `grant_table` 上该 `role_code` 的 USER / DEPT / POST 主体展开后的所有用户 |
| **PERMISSION** | 权限码 → `sys_role_permission` 桥角色码 → 同上 |
| **GRANT** | `GrantSubjectKey`：USER 经 `grant_table` 取 `subject_id`；DEPT/POST **不依赖** grant 现存行，经 `user_dept`+`dept_closure` / `user_post` 展开（grant 行可能已删） |
| **USER_DEPT** | 给定部门子树（`dept_closure`）上的 `user_dept` 成员；**不按** `sys_dept.status` 过滤；成员侧看 `user_dept.status IN (1, 2)` |
| **USER_POST** | 绑定该 `post_id` 的用户；看 `user_post.status IN (1, 2)` |
| **USER** | payload 里的 `userIds`，不做 SQL 反查 |

命中后对每个用户：

- 正常用户：`permVersion++` + **整包** `AuthProfile` refresh（roles + permissions + deptScope + permVersion）
- 异常/不可刷新用户：evict 画像（用户删除等路径另踢会话）

没有「只刷权限不刷数据范围」的分拆。

## 主数据 submit 条件（已落地）

```
主数据变更
  ├─ 影响 grant 展开 / 成员边 / scope / 业务码 / 启停 / 删除
  │     → submit 对应 Kind
  │     → Impact 反查 impactedUserIds
  │     → 正常：permVersion++ + AuthProfile 全量 refresh
  │     → 异常：evict
  └─ 仅展示字段（name / remark / orderNum；部门编码；岗位换部门等）
        → 不 submit
```

| 实体 | 现 submit 条件 | Kind |
|------|----------------|------|
| 部门 | `parentId` \| `status` \| 删除 \| move | `USER_DEPT` |
| 岗位 | `status` \| 删除 | `USER_POST` |
| 角色 | `roleCode` \| `status` \| 删除 \| 分配权限 \| `role_scope` | `ROLE` |
| 权限 | `permissionCode` \| `status` \| 删除 | `PERMISSION`（删除可补 `ROLE`） |
| 组织授权边（DEPT/POST） | 任意替换 | `GRANT` |
| 用户直连角色 / 成员边 / `user_scope` | 任意写 | `USER` |

部门 `updateMeta` **已收紧**：只有 parent 或 status 变了才失效；改名称/备注/排序/编码不刷。

## 边界与坑

1. **部门树 vs `role_scope` 锚点**  
   `USER_DEPT` 只刷**部门成员**。用户不是该部门成员，但角色的 `role_scope` 锚点落在变更子树里——其 `deptScope` 也会跟着闭包变，却**不会**被 `USER_DEPT` 命中。要兜住只能对相关角色再打 `ROLE`，或扩展反查。这是模型缺口，多刷几次糊不住。

2. **`deptScope` 展开**  
   `DeptClosureMapper#selectDescendantRowsByAncestorIds` 展开后代时 **不按** `status` / `is_deleted` 过滤；功能权限侧展开另有启用约束。部门 status 变更仍走 `USER_DEPT`，与 `AuthorizationImpactMapperDeptSqlContractTest` 一致。

3. **用户名等主档字段**  
   `SysUserServiceImpl` 对 username/email/phone/status 变更走的是 **踢会话**（`UserSessionRevocationTrigger`），不是授权失效流水线。删用户同样先清 grant、再踢会话。画像里的 `username` 靠重新登录重建，不靠 `USER` invalidate。

4. **用户直连角色为何不走 GRANT**  
   已知 `userId` 时直打 `USER` 更准，也避开「grant 行已删、USER 主体还去 `grant_table` 反查」的空集风险。组织主体必须展开成员，才用 `GRANT`。

## FAQ

- **哪些字段会触发？**  
  以画像构建依赖为准：`parentId` / `status` / 业务码（role、permission）/ 删除 / grant·成员·scope 关系。名称、备注、排序、部门编码、岗位换部门等**不触发**。

- **刷的是什么范围？**  
  不是改画像某一列，而是对 Impact（或 `USER` payload）命中的用户做 **`permVersion` + 整包 `AuthProfile` 重建**；不可刷新用户只 evict。用户集合由 `ROLE` / `PERMISSION` / `GRANT` / `USER_DEPT` / `USER_POST` / `USER` 各自规则决定。
